## a. Widgets in a collapsed sidebar expander: values and execution

Answer: yes on both. With the default `on_change="ignore"` an expander's body always runs, so `source`, `limit`, `min_score`, `max_saved`, `load_clicked`, `excel_path`, `export_clicked` are always bound.
How I know (ran it):
- Browser, prototype app: first load with all three expanders collapsed auto-loaded saved rows (the `load_saved(..., limit=max_saved)` path) and showed 2 rows. No NameError.
- Browser, probe app: slider `s2` (persist_state="session") inside an expander kept its value 1 across a collapse, a rerun, a switch to another view that does not draw it, and back.
- AppTest (`<S>/probe/t_probe.py`): with every expander collapsed, `find_source`=nih-guide, `find_rows`=500, `find_min_score`=0.0, `find_max_saved`=500 are present; after setting source=both and min score=35, switching to Profile and back to Find, both values were kept.
- Docs (1.67.0 `st.expander.__doc__`): "All expander content runs regardless of whether the expander is open or closed" for `on_change="ignore"`.
The existing `persist_state="session"` comment still holds; the expander changes nothing about it.

## b. Does an expander remember being opened? Label changes? `key`?

Ran it in the browser on the probe app (four expanders opened by click, then rerun, then a label change from `"X"` to `"X (score 1 and up)"`, then a view switch and back):

| Expander | after a plain rerun | after its label changed | after view switch and back |
| --- | --- | --- | --- |
| unkeyed, fixed label | open | n/a (stayed open) | closed |
| unkeyed, changing label | open | **closed** | closed |
| `key=`, changing label | open | **open** | closed |
| `key=`, `on_change="rerun"`, changing label | open | **closed** (session_state went false) | closed |

So: an expander remembers being opened across reruns of the same view. A changing label resets an unkeyed one (and hides the slider the user was dragging). A `key` with the default `on_change` prevents the reset on 1.67.0. No variant remembers being open across a switch to another view and back: all come back collapsed (`expanded=False`). Widget values inside survive regardless.
`st.expander` accepts `key` on 1.59.0: `uv run --project ... --with streamlit==1.59.0 --offline python -c "inspect.signature(st.expander)"` printed `(label, expanded=False, *, key=None, icon=None, type=..., width='stretch', on_change='ignore', args=None, kwargs=None)`. I did not run the label-change behaviour on 1.59 in a browser (unproven there).
Prototype gives every expander a key (`find_source_rows`, `find_display`, `find_export`) but keeps fixed labels.

## c. Keeping the database path for every view

Chosen: the keyed box in Settings plus a read of session state everywhere. It is the smallest correct way.

```python
# streamlit_app.py, top of the sidebar
db_path = os.path.expanduser(st.session_state.get("db_path", DEFAULT_DB))
...
settings_page(db_path, DEFAULT_DB)

# settings_page.py, first thing under the header
st.text_input("Database", value=default_db, key="db_path", persist_state="session", help="The file that holds your results, your profile, your applications and your settings.")
```

Why it is correct: an edit to the box puts the new value in `st.session_state["db_path"]` before the rerun starts, so the read at the top of the script already sees it in the same run that draws Settings. `persist_state="session"` keeps the value while Settings is not drawn.
Proof (ran it, browser, `<S>/proto-sidebar-data` holding `grants.sqlite3` with two DEFAULTDB rows and `second.sqlite3` with three SECONDDB rows, a profile for "SECONDDB Investigator" and one application "SECONDDB application"): typed `data/second.sqlite3` in Settings, then
- Settings caption: "saved in data/second.sqlite3, the file named under Database above."
- Find: sidebar "Database: data/second.sqlite3. Change it under Settings."; Load Saved Results showed 3 rows, all SECONDDB titles; caption "... for SECONDDB Investigator."
- Profile: "Ranking uses the built-in profile ... for SECONDDB Investigator."
- Apply: "Your text, your inputs and every model call for this application are stored in data/second.sqlite3."
- back to Settings: box still `data/second.sqlite3`.
Reload (new session): view back to Find, no indicator, Settings box `data/grants.sqlite3`. This matches HEAD, whose unkeyed box also resets on reload.
Alternative not taken: `bind="query-params"` (exists on 1.59 and 1.67) would keep the path across a reload by putting it in the URL. It changes reload behaviour and puts a file path in the URL, so it is a product call, not a prototype fact.
Existing behaviour kept, worth knowing: Find does not reload rows when the database changes while rows are already in the session (`scored_items` non-empty); the user presses Load Saved Results. HEAD behaves the same.
