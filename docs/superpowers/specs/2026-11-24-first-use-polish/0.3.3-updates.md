## A. Launch check

**The keys** (https://sparkle-project.org/documentation/customization/, **Sparkle**):
- `SUEnableAutomaticChecks`: unset means no checks until the user answers a permission prompt on the second launch. `YES` turns scheduled checks on with no prompt. `NO` turns them off with no prompt. The app sets `YES`.
- `SUScheduledCheckInterval`: seconds between scheduled checks, default 86400. Minimum one hour: `minimumUpdateCheckInterval` returns `60 * 60` and the scheduler raises a smaller value to it (`Sparkle/SPUUpdaterSettings.m` lines 377-388, `SPUUpdater.m` lines 568-572 at tag 2.10.1). The app leaves the default.
- `SUAutomaticallyUpdate`: download and install silently. Not set, and the 2026-11-23 plan rules it out because the disk image is over 100 MB (`docs/superpowers/plans/2026-11-23-in-app-updates.md:247`, **repo**).
- `SUAllowsAutomaticUpdates`: whether the update window offers the "install automatically" option. Not set, so Sparkle's default applies.

**Today's behaviour.** On start, `startUpdater` runs `startUpdateCycle` one run-loop later, unless a session is already in progress (`SPUUpdater.m` 175-188). With `SUEnableAutomaticChecks` set there is no prompt (`SPUUpdater.m` 406-409) and the scheduler compares now with `SULastCheckTime`; a missing date counts as `distantPast`, so the first launch checks at once, and later launches check only when a day has passed (`SPUUpdater.m` 551-588). **Sparkle**. So the app already checks at launch when the last check is over 24 hours old, and on the very first launch. A user who opens it daily may wait up to a day after a release.

**The documented way.** `SPUUpdater.h` (shipped header, `checkForUpdatesInBackground`): "If you want to additionally force an update check on every app launch though, it's recommended to only call this method immediately after starting the updater, and only when automatic update checks are enabled (by checking `automaticallyChecksForUpdates` is `YES`). Calling this method at later points could interfere with Sparkle's scheduler." The `startUpdater:` doc also allows any of the three check calls "after starting the updater and before the next runloop cycle". **Sparkle**. No plist key or delegate method does this. `checkForUpdateInformation` is a probe that never offers the update, so it does not fit.

**Interaction with the scheduler.** The explicit call sets `sessionInProgress` at once (`_checkForUpdatesInBackground`, `SPUUpdater.m` 603-606), so the scheduler's own launch cycle is skipped (`SPUUpdater.m` 185-187) and there is no double request. When the check ends, Sparkle records `SULastCheckTime` and schedules the next one an interval later (`SPUUpdater.m` 789, 822-833). **Sparkle**

**First launch and the permission prompt.** None, because the plist sets `SUEnableAutomaticChecks`. `checkForUpdatesInBackground` logs a warning only when that key is absent and checks are off (`SPUUpdater.m` 664-674). **Sparkle**

**What the user sees.** No update, or no network: nothing. The scheduled driver shows an error only after it has shown an update (`SPUScheduledUpdateDriver.m` 104-107, `showErrorToUser:_showedUpdate`), and the rehearsal's `--stop-feed` run saw no window at launch (`docs/superpowers/plans/2026-11-23-in-app-updates-evidence/sparkle-messages.txt:8`, **repo**). An update: the standard update window with the notes, Install Update, Skip This Version and Remind Me Later. For a regular Dock app a launch is an "opportune time", so it is shown then (https://sparkle-project.org/documentation/gentle-reminders/, **Sparkle**).

**Skip This Version.** Background checks do not find a skipped version ("Updates that have been skipped by the user will not be found", `SPUUpdater.h`), stored as `SUSkippedVersion` (`SUConstants.m:26`). The menu item still finds it (`checkForUpdates` "will find updates that the user has previously opted into skipping"). **Sparkle**. So a launch check does not nag about a skipped version. **Remind Me Later** is not a skip, so the window comes back at the next launch (inferred from the same code, **guess** on how users take it).

**The call, on the main thread, inside `start_updater`** (already the main thread via `AppHelper.callAfter`):

```python
def start_updater(framework: Path, log: Path) -> None:
    # Runs on the main thread. An app that cannot update must still open.
    try:
        UPDATER.append(sparkle_class(framework).alloc().initWithStartingUpdater_updaterDelegate_userDriverDelegate_(True, None, None))
        # Sparkle schedules a check once a day. SPUUpdater.h allows one more at launch, right after the start and only while automatic checks are on.
        updater = UPDATER[0].updater()
        if updater.automaticallyChecksForUpdates(): updater.checkForUpdatesInBackground()
    except Exception:
        with log.open("a") as out:
            out.write(f"{NAME} updater did not start:\n{traceback.format_exc()}")
```

Append first, so the menu item keeps its controller even if the check raises. PyObjC resolves `updater`, `automaticallyChecksForUpdates` and `checkForUpdatesInBackground` on the 2.10.1 framework in `macos/build/sparkle` (`instancesRespondToSelector_` true for all three). **measured** with `NIH Extractor/.venv/bin/python`.

**Before the updater has started** (a failed `startUpdater`): `checkForUpdatesInBackground` logs "updater hasn't been started yet" to the system log and returns (`SPUUpdater.m` 659-662, **Sparkle**). I made a controller with `startingUpdater=False` outside the bundle, called `updater().checkForUpdatesInBackground()`: no exception, `sessionInProgress` stayed false. **measured**. Off the main thread it re-dispatches itself to the main queue (`SPUUpdater.m` 649-656), but the launcher already calls it there.

**Existing tests on `start_updater`** (`NIH Extractor/tests/test_macos_launcher.py`): line 213 (a failed import is logged, `UPDATER` stays empty); line 305 (`wait_and_load` schedules `start_updater` before the server wait); line 320 (no PyObjCTools, still loads); line 340 (the controller is made with `(True, None, None)`, kept, and the menu item reaches `checkForUpdates_`). Line 340's fake controller is a `SimpleNamespace` without `updater`, so with the change it would raise inside the `try` and write "updater did not start" to the log while still passing. Give it `updater=lambda: SimpleNamespace(automaticallyChecksForUpdates=lambda: False)`.

@pytest.mark.parametrize("automatic", [True, False])
def test_the_updater_checks_at_launch_only_while_automatic_checks_are_on(monkeypatch, tmp_path, automatic) -> None:
    launcher = _load(monkeypatch)

## B. Is a check at every launch a good idea?

Sparkle allows it and says how (header above). Its only stated limit is the one-hour minimum on the scheduled interval, "to keep you from accidentally overloading your servers" (customization page). Costs: one HTTPS GET per launch to `github.com/.../releases/latest/download/appcast.xml`, which answers `302` to `release-assets.githubusercontent.com` (**measured** with `curl -I`); the feed is about 1 KB. Offline, the check fails silently and the app opens as before (above). The request tells GitHub the user's IP and that the app launched, which the daily check already did once a day.

Tradeoff for the risk list: a launch check shows a new release at the next launch instead of up to a day later, at the price of one small request to GitHub per launch that the user did not ask for. A user who clicks Remind Me Later sees the window again at every launch until they install or skip.

## C. Release notes in the window

- Inline `<description>` in the item: HTML in CDATA by default; `sparkle:format="plain-text"` since 2.4; `sparkle:format="markdown"` since 2.9 on macOS 12+ (https://sparkle-project.org/documentation/publishing/ "Embedded release notes"; CHANGELOG 2.9.0 "Add basic markdown support for release notes (requires macOS 12+)"). 2.10.1 supports all three. **Sparkle**
- `<sparkle:releaseNotesLink>`: Sparkle downloads it and picks the format from the MIME type or the extension, Markdown for `text/markdown` or `.md` (`SUUpdateAlert.m` 222-243). A GitHub release asset is served as `application/octet-stream` (**measured**), so a `.md` name would still render as Markdown. When an item has both, the link wins: the description is used only when `releaseNotesURL == nil` (`SUUpdateAlert.m` 181).
- `<sparkle:fullReleaseNotesLink>`: not shown in the update window. It is the version-history link offered when a manual check finds nothing (publishing page "Full release notes"). Optional.
- Rendering: Markdown and plain text go to an `NSTextView` (`SUTextViewReleaseNotesView`), not a web view, so there is no JavaScript and no remote loading. Markdown is parsed by Foundation's `initWithMarkdownString:options:nil` and restyled by Sparkle for headings, lists, block quotes and code (`SUTextViewReleaseNotesView.m` 100-300, 377-390). Links open only when `SUReleaseNotesIsSafeURL` passes (`SUTextViewReleaseNotesView.m` 120-135). Dark mode: `usesAdaptiveColorMappingForDarkAppearance = YES` (line 366). No size limit in the code I read; the box scrolls vertically. HTML notes would go to `WKWebView` with JavaScript off unless `SUEnableJavaScript` (customization page). **Sparkle**
- Proven in this repo: the 2026-11-23 spike saw "the app icon and the Markdown release notes" in Sparkle's window (`docs/superpowers/plans/2026-11-23-in-app-updates.md:684`). **repo**
- Effect on users already installed: the notes are read from the feed by the installed Sparkle, so 0.3.2 users see the 0.3.3 notes when 0.3.3 ships. The feed carries one item, so a user who skipped 0.3.2 sees only 0.3.3's notes. **inferred from the feed shape**

## E. Escaping and safety

- Inside CDATA, `&` and `<` need no escaping; only `]]>` ends the section. The split above round-trips: notes with `& < ]]> <b>x</b> $HOME \`id\`` parse back exactly with ElementTree, and `xmllint --noout` passes (**measured**, under bash 5.3 and `/bin/bash` 3.2, the runner's bash). Bash does not re-expand `$` or backticks inside a variable's value in an unquoted heredoc, which the test also covers.
- Inline HTML in the Markdown is not run: Markdown goes to an `NSTextView`, not a web view (C). Links pass `SUReleaseNotesIsSafeURL`.
- Tests that pin it (added to a scratch copy of `test_macos_appcast.py`, 8 passed, **measured**): `_run` gains `notes="- A fix."`, writes `tmp_path / "notes.md"` and sets `RELEASE_NOTES` in the env; then
