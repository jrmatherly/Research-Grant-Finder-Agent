## A. The alert sound

### How keys reach the page (read)

- `webview/platforms/cocoa.py` 6.2.1, `BrowserView.WebKitHost.keyDown_` (line 512). It handles only Command shortcuts (x, c, v, a, z, q, w). Every other key goes to `super().keyDown_(event)`, that is, WKWebView's own `keyDown:`. pywebview adds nothing that would swallow Escape or the arrows.
- driver.js 1.14.0 (vendored), function `mr` registers on `window`: `keydown` capture (`dr`, marks the key as handled), `keydown` bubble (`fr` then `ur`), `keyup` bubble (`pr`). Plus a gate (`cr`) on `keydown`/`keypress`/`keyup` capture that calls `preventDefault` only for a key inside the popover pressed under an earlier step's activation.
- The keys act on **keyup**: `pr` calls `tour.escape()`, `tour.arrowRight()` or `tour.arrowLeft()`. Nothing in driver.js calls `preventDefault` on the keydown of Escape, ArrowLeft or ArrowRight.
- The trap (read, then ran). `fr` removes the key from the handled set only when `!t.defaultPrevented`. If any listener prevents the keydown before `fr` runs, the key stays "handled" and `pr` ignores its keyup. So a `document` or capture-phase `keydown` listener that calls `preventDefault` breaks all three keys. Ran in Chrome: with such a listener on `document` (capture), ArrowRight and Escape did nothing (tour stayed at "1 of 6").
- Tab (read, ran): `ur` calls `preventDefault()` on every Tab keydown while the tour runs (its focus trap). In Chrome a Tab keydown during the tour came back `defaultPrevented: true`. So Tab has no beep risk. Enter and Space on a focused popover button press the button, which is a default action WebKit handles (guess, not measured).

### Why WebKit beeps

A WKWebView sends the keyDown to the web process. If no script prevents its default and WebKit has no default action for it (Escape has none, and the arrows scroll only when the page itself scrolls, while Streamlit scrolls an inner container), WebKit hands the event back to AppKit, it climbs the responder chain, and `-[NSResponder noResponderFor:]` calls `NSBeep` (the AppKit path is known behaviour, not read in source; the count below confirms the path).

### The fix (ran)

```js
// A keydown that no page script prevents goes back to macOS, which beeps. driver.js acts on keyup and ignores a key whose keydown was prevented before its own bubbling keydown listener, so this one is added after drive().
const quiet = e => { if (e.key === 'Escape' || e.key === 'ArrowLeft' || e.key === 'ArrowRight') e.preventDefault(); };
lib.driver({ ..., onDestroyed: () => window.removeEventListener('keydown', quiet), steps }).drive();
window.addEventListener('keydown', quiet);
```

The hook is `onDestroyed` (config key, read: `p=o.config.onDestroyed`, called on every destroy route with an active step). There is also `onDestroyStarted`, which **replaces** the destroy, so it is the wrong hook.

It must be a `window` bubble listener added after `.drive()`, so it runs after driver.js's own bubble `keydown` listener on the same target.

Chrome (ran, real CDP key presses, Streamlit page):
- ArrowRight, ArrowLeft and Escape still work: 1 → 2 → 5 of 6, ArrowLeft 5 → 4, Escape closed the tour.
- While the tour runs, a probe keydown for Escape and ArrowRight comes back `defaultPrevented: true`, and F13 comes back `false`.
- The listener is gone after each end route: Escape, the close button, Done (Next through 6 of 6), each followed by a probe that came back `false`. The overlay route does not exist once D is applied. With the 0.3.2 config the overlay click is one more destroy route through the same `onDestroyed` (read).

WKWebView (ran, about 25 s, a `python3.13` Dock icon). Script `<S>/proto-tour-wk/check.py`, listed in full under **Appendix**. It opens a pywebview 6.2.1 window with the vendored driver.js and the same glue, then sends real AppKit `NSEvent` keyDown/keyUp pairs through `-[NSWindow sendEvent:]`. Each page keydown arrives with `isTrusted: true`. The script replaces `-[NSWindow noResponderFor:]` with a counter, so the AppKit path that ends in `NSBeep` is counted instead of heard.

## C. Dark popover

- driver.css (read): `.driver-popover` has `color:#2d2d2d; background-color:#fff`. `.driver-popover-footer-btn` has `#2d2d2d` on `#fff` with border `#ccc`. Close button `#d2d2d2`, progress `#727272`. The arrow is `border:5px solid #fff`, and the `-side-*` classes make three sides transparent. No CSS variables for colours (only font, animation and instruction ones).
- Streamlit 1.67.0 sets no CSS custom properties on `:root` (ran: none starting `--st`, no `:root` rules). The theme lives in emotion classes. `.stApp` carries it: dark `rgb(23,22,20)` on `rgb(237,235,232)`, light `rgb(255,255,255)` on `rgb(47,45,43)` (ran).
- Why not `prefers-color-scheme`. Streamlit's theme menu offers "Use system setting" plus explicit Light and Dark (read: the string is in the 1.67 frontend, and the choice persists in localStorage `stActiveTheme-<path>`). An explicit choice can disagree with the media query. In the app, pywebview sets `NSRequiresAquaSystemAppearance = NO` (read, `cocoa.py` line 37), so the window follows macOS appearance, and WebKit's `prefers-color-scheme` follows it (guess from WebKit behaviour, not run in a WKWebView). That is why the owner got Streamlit dark while driver.js stayed white. The computed colours of `.stApp` are right in every case.
- Decision: at tour start, copy `.stApp`'s computed `background-color` and `color` into `--gm-tour-bg` and `--gm-tour-fg` on `<html>`. Then CSS appended in `styles()` uses them, falling back to driver.js's own colours.

```js
const app = document.querySelector('.stApp');
if (app) { const c = getComputedStyle(app); document.documentElement.style.setProperty('--gm-tour-bg', c.backgroundColor); document.documentElement.style.setProperty('--gm-tour-fg', c.color); }
```

## D. Overlay click

- Option (read): `overlayClickBehavior`, default `'close'`. Values `'close'`, `'nextStep'`, `'none'`, or a function. In `Cr`, `'none'` does nothing.
- Still closes the tour with `'none'` (read, then ran): Escape (`tour.escape` → `yr(e,'escape')`, gated on `allowClose`, which stays true), the close button, and Done on the last step. All three ran in Chrome with the option set.
- Prototype: `overlayClickBehavior: 'none'`. A dispatched pointer/mouse/click sequence on the overlay `path` (bottom right) left the tour open on "4 of 6". The same synthetic sequence on 0.3.2 closed it, so the test method does reach driver.js's handler (ran). Not tried with a real mouse.
- Tradeoff for the owner. With `'none'`, a stray click cannot throw away the tour, but a user who wants out must find the close button, Done, or Escape. With the default, a click anywhere outside is the quickest exit, and a mis-click ends the tour with no way back except Show me around.
